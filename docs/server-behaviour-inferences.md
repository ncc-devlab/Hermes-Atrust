# aTrust 服务端行为推断（供服务端实现对照）

本文面向 `Hermes-aTrust-Server` 的实现者。它**不描述 Hermes 客户端**，
而是把客户端对一台真实 aTrust 网关（`atrust.xidian.edu.cn`，含其数据面节点
`61.150.43.94:441`）的实测结果，**翻译成对服务端行为的推断**：一台服务端要与真实客户端
互通，需要表现出什么行为；哪些行为是可选的；哪些看似合理的实现会导致真实客户端失同步。

对方文档 `docs/protocol.md` 描述的是「本服务端实现了什么」。本文补的是另一半：
**「真实网关实际怎么做」**，两者可以逐条对照。凡有分歧，本文会明确指出。

## 怎么读这份文档

每条结论都带依据强度。这套分级来自 Hermes 的
[`open-questions.md`](open-questions.md)，含义在跨项目引用时必须保持一致：

| 级别 | 含义 |
|---|---|
| **L0** | 真实网关实测确认 |
| **L1** | zju-connect 源码（已被证实可用于真实 aTrust 网关） |
| **L2** | 由抓包与控制台表现**重建**的推测，**不构成证据** |
| **L3** | 纯推断，无外部依据 |

**L2 单独出现等同于「未验证」。** 这一点对本文的读者尤其重要：
`Hermes-aTrust-Server` 与 Hermes 客户端互通，只证明两个实现彼此一致，
不证明任何一个与真实网关一致。2026-07-31 的 VIP 长度 bug 正是被这种互证掩盖了两天——
两边都读 8 字节，互相都跑得通，而真实网关要求读 10。

**样本量诚实声明：** 本文的 L0 结论来自**一台网关、一个部署、一个学期的配置**。
它们是「这台真实网关这样做」，不是「aTrust 协议规定这样做」。凡是可外推性存疑的地方
都单独标注了。

## 1. 签名校验：真实网关两条路径都不校验

**级别：L0（2026-07-31 TCP 侧，2026-08-04 L3 侧）**

对方 `protocol.md` §4.4 描述了 `apply_sign_policy`（blank / raw / re-marshal 三种口径校验
`xRequestSig`），并说「TCP 与 L3 conntrack 鉴权均走 `apply_sign_policy`」。

**真实网关的实测行为是：两条路径都不校验 HMAC。**

实验方法（两组必须在同一会话内连续跑完，因为会话寿命有限，见 §7）：取一个已授权目标，
用正确的 `sign_key` 跑一次，再把 `sign_key` 的**首个十六进制字符翻转**（其余 63 字符完全相同）
跑第二次。

| 路径 | 正确 key | 坏 key | 结论 |
|---|---|---|---|
| TCP init（`05 01 81 53 03`） | 握手成功 | **握手成功** | 不校验 |
| L3 `0x13` flow auth | 返回 32 字节 connectToken | **返回 32 字节 connectToken** | 不校验 |

L3 侧还做了第三组：坏 key + **全新的五元组**（换源端口）。仍然授权。这一组是必须的——
前两组用的是完全相同的 flow key，若服务端对该流有缓存授权，第二组的成功就无法归因。

**对服务端实现的两条推断：**

1. **`apply_sign_policy` 的「严格校验」分支在真实网关上没有对应物。** 服务端当然可以实现
   它（更安全），但要意识到：**真实客户端可能携带一把服务端从未见过的 key**，
   因为客户端侧的 SignKey 来源本身就未确认（见下）。默认开启严格校验会拒绝真实客户端。
2. **「从 wire JSON 的 `signKey` 字段 first-write-wins 学习」这套模型，在 L3 路径上不可能成立。**
   L3 auth JSON **不携带 `signKey` 字段**——唯一与签名相关的字段是 `xRequestSig`。
   服务端根本收不到 key，因此无从学习。如果 `Hermes-aTrust-Server` 的 L3 路径实现了这个学习逻辑，
   它在协议上是无源之水；真实客户端不会触发它。

**仍未知：** SignKey 究竟是客户端生成、服务端下发，还是经某个尚未发现的注册接口绑定。
Hermes 目前使用一把临时随机 key，在真实网关上可用——但这只说明「这台网关不校验」，
不说明「协议不需要签名」。

**因此建议服务端把签名校验做成显式可配置，默认关闭，并在文档里标注这是与真实网关一致的选择。**

## 2. `appId` 裁决：任一覆盖候选均可，但无关项立即拒绝

**级别：L0（2026-08-03）**

对方 `protocol.md` §5.4 的 ACL 描述是「按策略中的 app / 节点组 / IP 或域名 / 端口 / 协议匹配；
不匹配则拒绝授权或丢包」。这个描述与实测一致，但**遗漏了重叠情形下的关键语义**。

真实资源表存在大量重叠：同一个目标 `IP:port` 会被多条资源条目覆盖，各自属于不同的 `appId`。
对同一目标分别用三种 `appId` 请求授权：

| `appId` 来源 | TCP tunnel | L3 flow auth |
|---|---|---|
| 最具体的匹配条目（specificity 优先） | 地址阶段通过 | 返回 connectToken |
| 服务端原始顺序第一条（first-match） | 地址阶段通过 | 返回 connectToken |
| 完全无关的 app | 立即 `0x02` | `auth status 0x82` |

**推断：网关校验的是「这个 `appId` 是否属于覆盖该目标的某条资源」，而不是「是否等于唯一正确的那一条」。**
它不强制 first-match，也不强制 specificity。

**对服务端实现的推断：** ACL 判定应当是**存在性检查**（该 appId 名下是否有一条资源覆盖此五元组），
而不是「先按某种排序选出唯一 appId，再比对客户端送来的是否等于它」。后者会拒绝合法客户端——
因为不同客户端实现的排序策略不同（zju-connect 的 L3 走 first-match，TCP 走 last-match 覆盖，
域名走 Go map 的不确定顺序；Hermes 走确定性 specificity）。

**外推限制：** 该实验样本中所有候选**同属一个 node group**。跨 node group 的重叠行为未测。

## 3. TCP 状态码的时序是可观测的行为签名

**级别：L0（2026-08-03）**

对方 `protocol.md` §4.2 的状态码表语义正确，但**没有记录时序**，而时序在实测中是区分两类失败的
唯一手段：

| 状态 | 何时出现 | 延迟 |
|---|---|---|
| `0x02`（不允许） | app 授权失败 | **立即**（~0.1 s） |
| `0x03`（网络不可达） | app 授权**通过**后，节点尝试连接目标失败 | **~15 s** |

**这条对客户端和服务端都有后果：**

- **客户端侧：** 默认 8 秒的握手超时会在 `0x03` 到达之前就报超时，于是「目标不可达」被错误地
  呈现为「握手超时」。任何要观察 `0x03` 的实验必须把握手超时设到 20 秒以上。
- **服务端侧：** 如果 `Hermes-aTrust-Server` 在上游 dial 失败时**立即**返回 `0x03`，
  它的行为与真实网关不同。这本身不影响互通，但会让「拿本服务端当 mock 来验证客户端超时逻辑」
  的实验得出与真机相反的结论——这正是 L2 循环论证的典型形态。

另外注意对方 §4.5 写的「失败在发送 `OK` 前用 `53 00` 错误文本回复」：实测中 app 授权失败
（`0x02`）出现在**地址阶段之后**，即客户端已经收到过 `53 00 OK`。两者不是同一个阶段。

## 4. `0x94` 双格式判别对服务端的硬约束

**级别：L1（判据来源）+ L0（真实样本）**

对方 `protocol.md` §5.3 只描述了 token 模式的载荷布局。**真实协议里 `0x94` 有两种布局，
且帧中没有任何标志位区分它们。** 客户端只能靠 body 头两字节的数值判别：

```text
n = u16be(body[0..2])
0 < n <= 4096   →  长度前缀分支：其后 n 字节是一个完整 IP 包
否则            →  token 帧分支：tokenLen | token | reserved(2) | count | [u16 len][pkt]...
```

**这给服务端两条必须遵守的不变量，否则任何标准客户端都会失同步：**

1. **`connectToken` 长度必须 ≥ 17 字节。**
   token 帧的头两字节是 `tokenLen * 256 + token[0]`。若 `tokenLen ≤ 15`，这个数值必然 ≤ 4095，
   落进长度前缀区间 → 客户端误判 → 按 token 首字节起算长度 → **流立即错位**。
   `tokenLen == 16 && token[0] == 0` 同样误判（数值恰为 4096）。
   实测真实网关的 token 是 **32 字节**（两个独立样本，不同 appId、不同会话、不同 VIP）。
2. **下行单个 IP 包不得超过 4096 字节**（在长度前缀分支下）。超过则数值落进 token 区间，同样错位。

**误判的症状不是解析报错，而是流错位**：后续每一帧边界都偏移，表现为「跑一会儿之后帧头不是 `05`」
「随机版本号错误」「隧道无征兆卡死」。症状离原因很远，所以这两条不变量值得在服务端侧
用断言固化。

**建议服务端加一条自检：发出 connectToken 前断言其长度 ≥ 17。** Hermes 客户端已在收到 token 时
对 `< 17` 发告警，两边对齐后这个 bug 类别就被封死了。

**仍未测：** token 帧分支和 `n > 4096` 区间在真实网关上**一次都没被触发过**。
两个 L0 样本都走的长度前缀分支（44 字节 TCP 应答）。因此 §5.3 描述的 token 布局本身
仍然只有 L1 依据。

## 5. VIP 应答帧：长度、语义与一个已知的实现陷阱

**级别：L0（实测）+ L1（长度表来源）**

对方 `protocol.md` §3.2 只给了「响应（示意）」。实测细节：

- `addressType = 1`（IPv4），VIP body **6 字节**；
- 前 4 字节是 IPv4 地址；**尾 2 字节实测恒为 `00 00`**；
- 同一 SID 在不同时间重连会拿到**不同的 VIP**（观测到 `10.210.29.48`、`10.210.29.114`、
  `10.210.29.200` 等），即 VIP 不与 SID 绑定。

**尾 2 字节不是掩码。** 曾有过「`18 00` = 24 位前缀」的假说，实测为 `00 00`，证伪。
参考客户端（zju-connect）从未读过这两个字节：它把 VIP 一律按 **`/32`** 配置到虚拟网卡，
「哪些流量进隧道」完全由资源表逐条下路由决定。因此这 2 字节目前**不进任何决策路径**。

**实现陷阱（值得服务端知道，因为它决定了你的帧必须怎么写）：** zju-connect 自身两处不一致——
`ip.go::getIP` 只读 8 字节整帧，`l3tunnelconn.go::authTunnel` 读 10。
**以 `authTunnel` 为准**，因为它的连接要继续复用。Hermes 曾照 `getIP` 实现，
结果长连接从第一帧起就错位。如果服务端在这里少发/多发 2 字节，
只有「Get-IP 后立刻断开」的客户端能用，「Get-IP 后复用连接」的客户端会全部失同步。

另外，Get-IP 阶段会夹带一条 `53 00` 嵌套协议消息，实测 body 为：

```json
{"code":0,"data":{"deviceID":"644B123B"},"message":"OK"}
```

注意这个 `deviceID` 是**短十六进制串**，与客户端在鉴权 JSON 里送的 32 字符 `deviceId`
形态完全不同，应当是服务端侧的另一个标识。

## 6. `53 00` 会在会话中途出现，不只在握手阶段

**级别：L0**

`53 00 <u16 len> <body>` 不是 Get-IP 专属。实测它会在**已建立的 L3 会话中途**出现。
客户端若把它判为版本错乱并杀会话，会误杀健康隧道（Hermes 早期就是这样，已修）。

**对服务端的推断：** 这是一条服务端可以随时插入的带内消息通道。
如果 `Hermes-aTrust-Server` 打算用它下发状态（会话被踢、策略变更、要求重新鉴权），
需要知道**当前客户端普遍不解析其内容**——Hermes 只计数并记录，zju-connect 直接跳过。
也就是说，通过这个通道下发的可操作状态目前会被静默丢弃，症状是
「隧道还在但所有流突然不通」。要真正用起来，得先和客户端约定 body 的 schema。

## 7. 会话寿命与失效信号

**级别：L0（一次观测）**

登录后保存的网关会话（Cookie + SID）在 **3 小时 40 分**后复用被拒：

```
code 75500002 / "The session is invalid"
```

**上界 < 3h40m；是绝对 TTL 还是空闲超时，这次观测无法区分**（两次使用之间没有任何请求，
两种模型都能解释）。区分实验：保存后每 30 分钟打一次 `onlineInfo`，看能否延过 3.7 小时。

**对服务端的推断，以及一条对客户端实现者的提醒：** 同一个业务码会经由**两个不同的接口**
到达客户端——`authConfig` 和 `clientResource` 都会返回它，而它们在客户端侧通常是不同的
错误类型。一个只在登录路径上处理该码的客户端，会在资源刷新路径上把它当成普通瞬时故障，
于是无限重试、无限告警，而整个运行时停在一张只会越来越旧的资源表上。

Hermes 的处理方式（供参考）：把该码识别为**不可重试的会话失效**，升级为独立事件，
不计入连续失败计数。服务端侧对应的建议是：**失效码要在所有会话相关接口上保持一致**，
不要在某些接口上退化成 401 或空响应，否则客户端无法统一识别。

## 8. 数据面节点的 TLS 行为：SNI 会让节点静默

**级别：L0（2026-07-31）**

这一条最容易在服务端实现里踩到，因为它反直觉：

**真实数据面节点在 ClientHello 携带任何 SNI 时静默不响应**——不是握手失败，不是 alert，
是不回包。客户端必须在建立数据面 TLS 时**关闭 SNI**。

其余观测：

- 节点证书是**自签的 `CN=sdp`**，不经过公共 PKI；客户端必须允许一个显式放宽的策略才能连上；
- TLS 握手实测 ~81 ms（同城）到 ~6.3 s（跨网、劣化链路）。**6.3 s 这个数字对超时设计很重要**：
  它与 8 秒的 flow-auth 超时非常接近，一个把连接预算设在 8 秒附近的客户端会把慢链路
  误报成鉴权失败。Hermes 现在把连接预算设为 20 秒。

**对服务端的推断：** 如果 `Hermes-aTrust-Server` 的数据面 TLS 要求 SNI 或依赖 SNI 做路由，
它与真实网关行为相反，真实客户端连不上。若要兼容，应当**接受不带 SNI 的 ClientHello**。

## 9. 若干常量与规模，供实现与压测参考

**级别：L1（常量来源）+ L0（规模实测）**

| 项 | 值 | 依据 |
|---|---|---|
| 心跳周期 | 25 s（`05 15 00 00` / `05 95`） | L1；真实网关容忍，未测容忍窗口上界 |
| flow auth 超时 | 8 s | L1；服务端从未声明 |
| flow key 格式 | `{atype}:{src}:{sport}-{dst}:{dport}`，**不含协议号** | L1，逐字符一致 |
| 鉴权 JSON 里的 `atype` | `0x0800`（EtherType） | 与 flow key 里的 `4` 是**不同命名空间** |
| L3 授权 URL 前缀 | `tcp:`（**无 `//`**） | L1 |
| Get-IP 请求长度字段 | **动态**，按 SID JSON 长度计算 | L1；`0x0053`=83 只是 73 字符 SID 的巧合 |
| 隧道 MTU | 1400（客户端侧硬编码，不协商） | L1 |
| `clientResource` 规模 | ~1.3 MB / 12.5 s，1361 IP + 523 域名资源，1 个 node group（2 端点） | L0 |

**`flow key 不含协议号` 有一个未验证的后果**：同四元组的 TCP 流与 UDP 流会**共用一条 conntrack
表项**。这是服务端的真实语义，还是参考客户端一个恰好没被踩到的简化，目前无依据。
真踩到时的症状是「UDP 流复用了 TCP 流的 connectToken」。
**如果 `Hermes-aTrust-Server` 的 conntrack 键包含协议号，就会与客户端不一致**，
建议先按不含协议号实现，并把这一条列为待验证项。

**`clientResource` 的 12.5 秒**值得单独说：这不是超时，是正常响应时间。
客户端若把该接口的超时设得太短会误判。服务端侧若要做性能对齐，这是真实基线。

## 10. 已知未测项（不要据本文假设它们已确认）

按对服务端实现的影响排序：

1. **`0x94` token 分支从未被真实网关触发。** §4 的 token 布局仍只有 L1 依据。
   下行 > 4096 字节的行为完全未测——上行受 MTU 1400 约束不会越界，
   **下行没有任何东西保证服务端不发更大的包**。
2. **长会话存活。** 25 秒心跳来自参考客户端源码，真实网关的容忍窗口未知。
   心跳过慢会被静默断开，过快在大规模部署下可能触发限流。
3. **并发多流。** conntrack 驱逐、并发授权去重、waiter 管理目前只有本地 mock 覆盖。
4. **`0x16` / `0x96` second VIP。** 请求触发条件与用途均未确认。
   已知 `addrType = 5` 的 VIP 帧本身就同时带 IPv4 和 IPv6，
   与 second-VIP 是否互斥、还是服务不同场景，无依据。Hermes 能解码 `0x96` 但从不主动发 `0x16`。
5. **`addrType = 4`（18 字节）和 `5`（22 字节）的 VIP 帧**在真实网关上从未观察到，
   长度表仍来自参考客户端。
6. **ICMP 如何命中资源。** 参考客户端的判据是 `protocol == "icmp" || == "all"` 且不比较端口，
   但其解析器会提前过滤显式 `icmp` 条目——**parser 与 matcher 自相矛盾**。
   Hermes 两者都解析并匹配，不复制这个不一致。真实网关的语义未测。
7. **域名通配符语义。** 现按 `*.example.edu` 覆盖任意子域但不含 apex 实现，服务端是否同此未确认。
8. **未知 `05 <cmd>` 的帧头形状。** 已知 `0x93` / `0x96` 在 u16 长度**之前**多一个 status 字节
   （5 字节头），`0x95` 和未知命令用通用 `<u16 len>`（4 字节头）。
   **但这个名单是枚举出来的，不是规则**——没有任何依据说明下一个新命令属于哪一类。
   若服务端要新增命令字，**建议采用通用 4 字节头**，因为这是现有客户端跳过未知命令时的假设；
   采用 status-先于-长度 的布局会让客户端读少 1 字节并静默错位。

## 11. 复现方式

上述 L0 结论全部由 `atrust-probe` 产生，命令、判读表和原始实验记录在
[`open-questions.md`](open-questions.md)（章节 E1–E9、E3b）。该文档同时记录了
每条结论的二义区间和误判症状。

实验纪律里有三条与本文结论直接相关，跨项目复现时必须保持：

1. **数据面节点地址写 IP**，因为控制面域名解析到的是另一个（死）端口；
2. **数据面 TLS 必须放宽校验**（自签 `CN=sdp`）**且关闭 SNI**（§8）；
3. **需要正负对照的实验必须在同一个会话内连续跑完**，中间不能夹一次重新登录（§7）。

会话文件与 trace 文件含实时凭据（Cookie、SID、SignKey、登录 POST body），
强制 `0600`，**不得随报告或 issue 分发**。可分发的只有 `--log-file` 的内容——
它按设计只记录存在性、计数、状态码和耗时。本文中出现的所有数值都取自后者。
